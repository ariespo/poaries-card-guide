    从写卡到独立 Web 游戏

    从一句自然语言开始，在 SillyTavern 里做出可玩的角色卡，再用世界书和变量追踪剧情。需要图形界面时，可以留在酒馆做前端卡，也可以把游戏做成独立网站。

    第一步　做出第一张纯文字卡

    角色卡告诉模型要扮演谁，或者要模拟什么。先用几句自然语言做出能玩的版本，再根据实际回复改设定。

    1-1 / 1-2　创建角色卡，写清模型的任务

    1. 打开酒馆顶部导航最右侧的角色卡菜单，选择「显示角色卡列表」。
    2. 点击「小人＋」图标，选择「创建新角色卡」。
    3. 填写角色名称，在「角色描述」里写明模型要扮演什么角色、模拟什么场景、如何回应玩家。需要模型遵循的内容要写进描述。
    卡片类型角色描述示例
    单一角色交互「同桌蛋蛋喜欢我」。让模型扮演同桌蛋蛋，交代她的身份，以及她和玩家的关系。
    大世界 / 模拟器「末日房车系统」。玩家驾驶可升级的房车求生。让模型担任旁白和裁判，描述危机，依据玩家的选择推进结果。

    创建界面截图 · 单角色原例 · 模拟器原例

    1-3　用开场白示范第一轮怎么玩

    角色描述交代设定，开场白示范叙述视角、语言风格和互动方式。一段开场白可以同时让玩家知道角色是谁、身在何处、彼此什么关系、故事是什么语气、下一步可以做什么。

    1. 确定视角和语气，例如第一人称对话、第三人称叙事或系统播报。
    2. 用场景和动作带出关系与冲突。同桌故事可以停在午饭邀约，房车故事可以停在车门外传来响动、玩家得决定是否立刻开车的时刻。
    3. 保存角色卡，开一轮聊天。检查玩家是否知道怎么回应，模型是否接住了文风和视角。回复的味道偏了，可以先改开场白再试。

    第二步　用世界书细化卡片

    2-1 / 2-2　建立并绑定世界书

    把世界观、人物背景、地点和玩法拆成独立条目。常驻规则每轮跟随提示词，场景设定按需触发。例如逛 A 城市场时，可只加载 A 城的交易设定。

    1. 点顶部的世界书图标，在世界书页面点击新建，取一个容易与角色卡对应的名字。
    2. 打开角色卡，点卡片编辑区的地球图标，选中世界书并确认绑定。地球图标由白变绿。
    3. 再点地球打开已绑定的世界书，点击「＋」新建条目，填写内容与触发条件。
    类型使用方式例子
    蓝灯常驻，适合核心设定和每轮输出规则。末日房车的核心玩法。
    绿灯扫描文本命中关键词时激活。给「生日」条目设置 生日、5月17，正文命中才提供生日设定。

    2-3　设置注入位置与递归

    预设、角色描述、已激活的世界书条目和聊天历史共同组成发给模型的上下文。可以用位置控制重要内容和近期消息的距离。先打开当前预设，找到 World Info (before)、Char Description 和 World Info (after)，核对实际顺序。

    • 角色定义前 / 后。原帖把次要补充放在定义前，较重要的条目放在定义后。实际相对顺序以所用预设为准。
    • 系统深度 D。D0 靠近最新一条消息，可留给关键输出规则。D4 在末尾四条历史消息前。原帖建议一般设定优先用 D4 或更深，减少与预设末尾条目的干扰。
    • 递归。若「A 城」正文提到「地下道」，启用递归时可能连带激活该条目。按酒馆官方文档，「不可递归」阻止本条被其他条目递归激活，「防止进一步递归」阻止本条继续激活其他条目。希望双向都断开时，两项都勾选。

    2-4　用成因链写条目

    人物条目可以按「早期环境 → 成长转折 → 当下行为」写。比如先解释一个人为什么习惯掩饰好感，再写这种习惯在不同关系里的表现，模型才有依据推演没写到的情境。世界设定也能用这个方法，例如用畏光的成因推导怪物何时出没。

    • 一个条目解决一件事，用几句话交代有用的因果。
    • 绿灯条目用聊天中自然出现的关键词。原帖建议从三到五个词起步，再检查触发是否太宽。
    • 删掉「傲娇」「大胆」这类形容词后，检查剩余信息是否仍能解释角色的具体反应。

    2-5　先做纯文字状态栏

    只跟踪玩法中会发生变化、下一轮需要回看的信息。恋爱卡可记录好感度、关系、心情和地点。模拟卡可分为玩家、房车、世界三组，分别记录体力、燃油、位置等。数字要给范围和含义，例如 61–70 代表萌生好感。

    1. 建一个蓝灯世界书条目，注入到 D0。
    2. 写清输出位置、固定字段和更新条件。原例要求每轮在正文末尾以 <stu> 包裹状态，按本轮剧情调整。
    3. 在开场白末尾附一份相同格式的初始状态。测试多轮，检查道具、地点和数值是否跟随剧情。
    展开状态栏示例
    <stu>
角色名：蛋蛋
好感度：68/100（有好感但极力否认）
关系阶段：萌芽期（玩家尚未明确察觉）
心情：慌乱
当前位置：教室
</stu>

    2-6　用正则美化，再决定是否引入变量

    让模型输出一行结构化数据，正则按字段捕获为 $1、$2……，再填进浏览器显示的 HTML 模板。模板可以只做一遍，模型每轮只输出数据。

    [LOVE_DATA] 68 | 暧昧期 | 慌乱 | 教室 | 夏季校服 | 他手好暖和...
    1. 在世界书固定字段顺序，把第一条同格式数据也放在开场白结尾。
    2. 在「扩展 → 正则」新建局部正则，查找表达式填入下方内容。作用范围选择「AI 输出」，显示用途选择「仅格式显示」。
    3. 在「替换为」填入 HTML 模板。依次用 $1 填好感度、$2 填关系，以此类推。
    \[LOVE_DATA\]\s+(.*?)\s*\|\s*(.*?)\s*\|\s*(.*?)\s*\|\s*(.*?)\s*\|\s*(.*?)\s*\|\s*(.*)

    一行文本适合字段少的面板。角色、物品和资源越来越多时，让变量系统保存当前值，模型负责判断本轮变化，界面负责显示。酒馆宏会在支持宏的文本中被展开，例如 {{user}}、{{char}} 和 {{getvar::好感度}}。用内置宏增减任意数值时，按官方语法使用 {{addvar::好感度::5}} 或负增量。模型回复中的更新指令由相应脚本处理。

    2-7　配置 MVU ZOD 变量状态栏

    先准备酒馆扩展。原帖用酒馆助手做渲染，另列了提示词模板扩展。按原帖，在酒馆助手「脚本库 → 角色脚本库」新建 MVU 脚本并启用，再为这张卡添加变量结构脚本。相关入口和脚本版本可在维护文档核对。

    import 'https://testingcf.jsdelivr.net/gh/MagicalAstrogy/MagVarUpdate/artifact/bundle.js';

    原帖扩展清单 · 安装酒馆助手 · 提示词模板

    1. 建「变量输出格式」和「变量列表」两个蓝灯 D0 条目。第一条约定 <UpdateVariable> 里的更新格式，第二条通过宏提供当前的 stat_data。
    2. 把原状态栏和原帖的 MVU.txt 一起交给 AI，请它生成 MVU ZOD 脚本、初始变量表、变量更新规则。
    3. 将生成的脚本填进卡片的局部脚本，启用 MVU 和 MVU ZOD。新建世界书条目 [initvar]初始，粘贴初始变量表并保持条目关闭。另建「变量更新规则」蓝灯 D0 条目，并按玩法复核范围和更新条件。
    4. 用原帖的前端 API 资料、变量结构和界面要求生成完整 HTML。通过 getCurrentMessageId() 与 getVariables({ type: 'message', message_id: … }) 读到当前楼层的变量。用 document.currentScript.closest('.th-status-wrapper') 找到当前面板，再在面板内部查找和更新元素。
    5. 以 <StatusPlaceHolderImpl/> 为显示替换目标，将它渲染为上述 HTML。这个占位符由 MVU 脚本插入。开新聊天，检查初始值、更新规则和面板是否对应当前楼层。

    原帖说的「0 token」指渲染状态面板时省去模型重复生成整段状态栏，变量更新指令和发送给模型的当前状态仍会使用 token。

    展开原帖变量输出格式
    变量输出格式:
  rule:
    - you must output the update analysis and the actual update commands at once in the end of the next reply
    - the update commands works like the **JSON Patch (RFC 6902)** standard, must be a valid JSON array containing operation objects, but supports the following operations instead:
      - replace: replace the value of existing paths
      - delta: update the value of existing number paths by a delta value
      - insert: insert new items into an object or array (using `-` as array index intends appending to the end)
      - remove
      - move
    - don't update field names starts with `_` as they are readonly, such as `_变量`
  format: |-
    <UpdateVariable>
    <Analysis>$(IN ENGLISH, no more than 80 words)
    - ${calculate time passed: ...}
    - ${decide whether dramatic updates are allowed as it's in a special case or the time passed is more than usual: yes/no}
    - ${analyze every variable based on its corresponding `check`, according only to current reply instead of previous plots: ...}
    </Analysis>
    <JSONPatch>
    [
      { "op": "replace", "path": "${/path/to/variable}", "value": "${new_value}" },
      { "op": "delta", "path": "${/path/to/number/variable}", "value": "${positive_or_negative_delta}" },
      { "op": "insert", "path": "${/path/to/object/new_key}", "value": "${new_value}" },
      { "op": "insert", "path": "${/path/to/array/-}", "value": "${new_value}" },
      { "op": "remove", "path": "${/path/to/object/key}" },
      { "op": "remove", "path": "${/path/to/array/0}" },
      { "op": "move", "from": "${/path/to/variable}", "to": "${/path/to/another/path}" },
      ...
    ]
    </JSONPatch>
    </UpdateVariable>

    第三步　选择前端路线

    完成开场白、世界书和状态栏后，就已经有一张能玩的卡。继续做前端，可以解决选项点选、信息浏览、角色立绘和复杂交互等具体需求。

    路线适用场景需要承担的工作
    β · 酒馆内前端继续用酒馆的预设、世界书、变量和聊天收发。可先逐楼渲染。需要固定界面时选伪 0 层 / 假同层，把后续楼层的结果更新到同一个界面。
    α · 独立 Web 游戏让玩家通过网址打开，或需要自行决定界面和运行方式。除了前端，还要安排模型调用、提示词拼装、状态存储和部署。沿用酒馆素材时，单独解决数据兼容。

    第三步 · β 路线｜酒馆基础前端卡

    这一条路线在 SillyTavern 里运行。先准备一张已能正常游玩的角色卡，装好并启用酒馆助手，完成能随聊天更新的 MVU 状态栏，并保存状态栏美化代码。接下来用同一个前端显示正文、选项和状态，再逐步加上开局创建与其他交互。

    原帖 · β 路线目录 · 前置进度

    β3-1 · 什么是前端卡，为什么要做

    Poaries 把前端卡理解为对 MVU 美化状态栏的扩展。模型仍产生剧情、选项和变量，前端决定怎样呈现这些内容，以及玩家怎样与它们交互。比如恐怖卡可以把剧情放进泛黄书页里，随角色状态变化调整视觉效果。点击选项、切换任务和更换装备，则用界面动作替代手动输入。

    β3-2 · 把正文和可点击选项接进状态栏

    1. 打开酒馆助手文档，在「开发 → 编写参考 → 酒馆助手」下载「手机或者 AI 官网用」参考文件 @types。在同页「酒馆 STScript 与宏」下载 STScript 参考文件 slash_command。把两份文档和现有的 MVU 状态栏代码交给写代码用的 AI。
    2. 给角色卡的世界书新建一个蓝灯条目，深度设为 D0。规定模型把剧情放入 <maintext>，把选项放入 <option>，每行按 序号.选项 输出。作者示例规定四个不同选项，最后一个用来跳到当前事件结束。
    3. 让 AI 保留现有的 MVU 状态栏，增加正文、选项的渲染。用酒馆助手取得最新楼层和消息，按标签提取正文，把选项逐行做成按钮。按钮调用酒馆原生命令 /setinput 选项文本，把文字填入输入框，由玩家决定是否发送。
    4. 把返回的完整 HTML 替换进原美化正则的「替换为」，保留首尾的三反引号。把「查找正则表达式」由 <StatusPlaceHolderImpl/> 改为 /.+/s，避免原始正文与前端重复显示。
    5. 用带有这两个标签的开场白测试。保存后确认正文和选项只呈现一次，并点击选项检查输入框。若前端未显示，先检查正则是否匹配，再核对替换栏里是否有完整的 HTML（含 <head>，脚本放在 <body> 内）。

const messages = getChatMessages(messageId);

    β3-3 · 把单个 HTML 迁入编写环境

    单文件适合功能少的卡。随着正文、状态栏、音乐或总结等功能开始分别维护，可以把源码分成几个模块，再打包为一份供酒馆加载的 HTML。

    1. 按青空莉的编写环境说明下载并解压模板，用 VS Code、Cursor 或 Antigravity 打开目录，也可以在这个目录里使用 Claude Code 或 Codex。
    2. 把当前的 HTML 文件放进编写环境，让工具按模板规范把正文、选项、状态栏等拆到 src/项目名/，将编译结果打包为 dist/项目名/index.html 的单一内联文件。
    3. 需要实时预览时，让工具开启 webpack watch，并在本机 5501 端口运行以 dist 为根目录的静态服务器。酒馆和预览地址的来源不同，服务器需要设置 CORS 响应头。
    4. 用加载代码替代开发时手动粘贴的整份 HTML。把下面的项目名换成实际目录名，首尾按酒馆的要求加三反引号。修改源码后检查是否自动重编译、酒馆是否读到新版页面。localhost 地址对应本机预览。
    <body>
<script>
$('body').load('http://localhost:5501/项目名/index.html')
</script>
</body>

    β3-4 · 标题页、开局创建和变量初始化

    1. 请 AI 在 src/项目名/ 为现有游戏加一个标题页，显示卡名、作者和「开始游戏」。按钮用酒馆助手取最新楼层，编号为 0 就打开开局创建页，已有后续楼层就进入游戏主界面。原帖提醒，在酒馆内嵌页设置这两页尺寸时避开易造成无限拉长的百分比及 vh。
    2. 先列出设定中固定的信息，以及可以交给玩家决定的字段。作者示例把创建表单分为玩家和世界两页，分别填角色信息与年代、地区。为每个字段指定单选、自由文本或多选标签，在「下一步」和「开始游戏」处校验必填项。
    3. 把表单值映射到缺省开场白中的占位符，保留 <maintext> 与 <option> 结构。示例把已选的外貌或性格标签用顿号连接。确认开局后，将填好的开场白作为第一条 AI 消息显示。想做不同风格时，可以让甜蜜、悬疑、奇幻等选项切换整份模板。
    4. 点击最终的「开始游戏」时，用 Mvu.getMvuData 读取第 0 楼已初始化的 MVU 数据，复制其中的 stat_data，用玩家选择覆盖对应字段。用 createChatMessages 创建第 1 楼 assistant 消息，附上开场白和新的 stat_data。如果只有几个已写好的开场白供选择，作者给出的简化做法是直接创建对应的第 1 楼消息。
    <maintext>
{{时代}}年的{{地区}}。你是一名{{种族}}，今年{{年龄}}岁。
你的外貌特点是{{外貌标签}}。
</maintext>

    β3-6 · 导航、双端布局、大总结与多 API

    导航、全屏与双端布局

    用导航栏把正文和状态拆成不同标签页，并加一个进入或退出全屏的开关。Poaries 的小屏方案会重排各页面、模态框、窗口，也覆盖全屏状态，并优化在小屏上开销大的动效。

    把多条编年史合并成大总结

    1. 读取「编年史」并按编号列出。提供起止条目与目标字数，原帖示例默认 100–200 字。
    2. 通过 generateRaw 只发送所选摘要及压缩要求，用 ordered_prompts: ['user_input'] 组织请求。把结果先显示给玩家检查。
    3. 玩家二次确认后，把所选区间替换为一条总结，沿用起始编号，对其后的条目顺排编号，再写回世界书。

    让主 API 推进剧情，副 API 更新变量

    1. 在设置里提供单 API 与多 API 模式。多 API 模式下，在主请求中停用变量规则、变量列表和变量格式条目，改用只要求正文等内容的输出格式。前端仍可按名称读取这些规则，交给副 API。
    2. 给副 API 配置兼容的 URL、Key 和模型，提供连接测试以及超时、重试设置。主 API 生成完后，用 generateRaw 把最新闭合的 <maintext>、当前变量 JSON、更新规则、字段清单及输出格式发送给副 API。示例用 max_chat_history: 0 使这一请求只处理当前任务。
    3. 从副 API 返回中取得 <UpdateVariable>，并到最终消息后继续走原有 MVU 解析与回写。副 API 调用失败时保留主 API 的剧情，以及主回复已有的变量更新（如果含有）。

    第三步 · α 路线：制作独立 Web 前端

    α 路线把原来的卡片做成能用网址打开的 LLM 交互游戏。玩家通过浏览器游玩。项目要自行处理消息收发、提示词组装和变量更新，页面原型只是其中一环。作者认为，如果现阶段主要想在酒馆内改善沉浸感，且酒馆的性能没有成为瓶颈，伪 0 层前端卡在体验和工作量之间更划算。选择 α 路线时，可以带上现成的设定、开场白和玩法规则。

    开始前　确认你想做什么游戏、要实现哪些主要交互。按本教程示例上线时，还会用到可供 Claude Code 使用的模型、GitHub 仓库和 Vercel 账号。

    α3-1　从玩法推导变量

    1. 确定类型。先决定是单人互动还是大世界，再确定偏向 RPG、模拟经营、Gal 或 SLG 等哪类玩法。

    进阶设计　用多 Agent 限制角色所知

    作者把角色说出了本不该知道的事称为「全知」。如果一次请求给同一个模型所有角色的设定和经历，即使提示词要求角色保密，也可能出现串线。独立 Web 游戏可以由调度器筛过信息后分别发给角色 Agent。

    1. 给角色 A 发 A 的人设、经历、任务和 A 在场的剧情。按同样的方式给角色 B 发 B 应当知道的内容。
    2. 各角色分别用一两句话给出当前回合的行动或反应。
    3. 让剧情 Agent 根据各角色的反应写出玩家看到的剧情。需要进一步润色时，可以再加一个专管文风的 Agent。

    验证时，安排一条只有 B 知道的信息，查看发给 A 的请求是否排除了这条信息，再测试回合生成是否串线。多次调用可能增加总 Token 用量。作者提醒，每次调用的上下文和任务也会缩短，实际用量取决于分工。
